Fast URL spam / ads / security-risk classifier

Bachelor's thesis or compact Master's project thesis

Build a URL-only classifier that learns from existing spam, ads, and security-risk URLs, then scores new URLs with a very small inference cost.

URL-onlyfast inferencegeneralises wellsecurity risk

Why this fits

  • URL strings carry strong lexical and structural cues, so the model can stay lightweight.
  • Character n-grams and hashed features usually generalise better than hand-written domain rules.
  • A linear model can be exported compactly and evaluated in microseconds per URL.

Suggested approach

  • Collect positive examples from existing spam, ad, and security-risk URL sets, then balance them with benign URLs.
  • Train a compact character n-gram model, such as hashed logistic regression or a linear SVM with calibration.
  • Validate on held-out domains and path patterns to measure generalisation, not just memorisation.

Entry task: Given a small labelled URL dataset, implement a character n-gram feature extractor and train a logistic regression classifier. Report precision, recall, and inference time per URL.

Target output: Binary risk score plus probability estimate for fast filtering, triage, or pre-screening in the OUR²S pipeline.

OUR²S ranking profiles with lightweight client-side XGBoost re-ranking

Master's thesis or research prototype

Design profile-based ranking for the OUR²S search engine, where clients submit compact XGBoost parameter profiles with the query and the server re-ranks against the requested profile.

rankingOUR²SXGBoostprofiles

Why this fits

  • Different ranking profiles can surface meaningfully different result orders without changing the underlying index.
  • Client-side profile selection keeps the system flexible while preserving a fast server-side ranking path.
  • Discovering a set of diverse profiles is naturally an unsupervised problem about coverage, separation, and ranking diversity.

Suggested approach

  • Define a small set of feature and parameter profiles for XGBoost learning-to-rank, with each profile tuned for a distinct ranking bias.
  • On the server, search for 20 to 30 profiles that maximise ranking differences on average queries while staying stable and explainable.
  • Assign human-readable names to the resulting profiles so clients can request them directly alongside the search request.

Entry task: Using a provided OUR²S query log sample, cluster queries by result-feature distributions and identify two or three clearly distinct ranking biases. Describe each in plain language.

Target output: A named profile family, client-requestable ranking configuration, and a diversity-oriented profile discovery method.

Large-scale hierarchical multilabel classification for OpenWebIndex categories

Master's thesis

Build a large-scale hierarchical classification dataset for OpenWebIndex pages based on the Curlie category hierarchy, then develop and evaluate a fast multilabel classifier using Jina v5 embeddings against TF-IDF and BM25-based baselines.

OpenWebIndexCurlie hierarchymultilabelJina v5

Why this fits

  • The current category assignment is rule-based, so there is a clear opportunity to build a stronger data-driven classifier.
  • The Curlie taxonomy introduces a realistic hierarchical label space rather than a flat single-label benchmark.
  • The comparison between embedding-based and lexical retrieval-style methods is practically important because TF-IDF or BM25 classifiers may be much cheaper and faster at scale.

Suggested approach

  • Construct a large-scale training and evaluation dataset from OpenWebIndex pages and Curlie-aligned category signals, with careful handling of hierarchy, multilabel assignments, and noisy labels.
  • Use Jina v5 embeddings to build a fast multilabel classifier, for example with nearest-neighbour, centroid-based, or lightweight linear classification layers on top of embeddings.
  • Benchmark against TF-IDF and BM25-style lexical baselines with attention to both effectiveness and system cost, including throughput, latency, memory, and indexing complexity.

Entry task: Given 1000 labelled web pages from the Curlie dataset, train a TF-IDF logistic regression classifier and report precision@1 and precision@3 on a held-out set. Describe where it fails.

Target output: A reusable hierarchical multilabel dataset, an embedding-based classifier, strong lexical baselines, and a clear effectiveness-versus-efficiency comparison for large-scale category assignment.

Learning sparse embeddings using Explicit Semantic Analysis

Master's thesis

Develop sparse, interpretable document embeddings using a reference corpus such as Wikipedia: represent each document by its strongest similarities to Wikipedia pages rather than by a dense latent vector.

sparse embeddingsWikipediaESAindexing

Why this fits

  • Explicit Semantic Analysis makes embedding dimensions interpretable because each active dimension corresponds to a reference document or concept.
  • A sparse top-k representation can support efficient indexing while preserving semantic evidence through Wikipedia page IDs and similarity scores.
  • The approach offers a useful contrast to dense embedding retrieval: more transparent dimensions, explicit pruning choices, and different storage/query trade-offs.

Suggested approach

  • Build or reuse an embedding pipeline for a reference corpus such as Wikipedia, producing one vector per Wikipedia page.
  • Embed an input document and compute its inner product against the embedded reference corpus.
  • Keep only the top-k or top-percentage Wikipedia pages according to similarity score; store the selected page IDs and scores as the sparse index vector.
  • Evaluate retrieval quality, sparsity, interpretability, and indexing cost against dense embedding and lexical baselines.

Entry task: Embed a small Wikipedia subset and a small document collection with one dense encoder. For each document, compute inner products against the Wikipedia subset, keep the top 20 reference pages, and inspect whether the selected pages form a useful semantic explanation.

Target output: A scalable ESA-style sparse embedding pipeline, pruning strategy for top-k or score-based selection, and an evaluation of retrieval quality, interpretability, storage cost, and indexing speed.

Evaluating LLM summaries of arXiv papers with generated questions

Master's thesis

Study whether LLM-generated summaries of arXiv papers preserve the information needed to answer questions about the source paper. Generate k question-and-answer pairs per paper, create summaries with different models and techniques, and measure how well the questions can be answered from each summary alone.

arXivsummarisationLLMsquestion answering

Why this fits

  • A short summary is useful only when it retains the paper's important claims, methods, results, and limitations.
  • Question answering provides a concrete, repeatable way to test whether a summary preserves this information rather than merely sounding plausible.
  • Comparing models, summarisation strategies, and paper corpora can reveal when summaries are faithful and which kinds of scientific content are lost.

Suggested approach

  • Build one or more arXiv paper corpora, for example from computer science, physics, or biomedical domains, with appropriate train, development, and held-out evaluation splits.
  • Use an LLM to generate k diverse question-and-answer pairs per paper, covering motivation, methods, results, evidence, and limitations; validate a sample for answerability and grounding in the full paper.
  • Generate paper summaries using several LLMs and techniques, such as direct prompting, section-aware summarisation, map-reduce or hierarchical summarisation, and iterative refinement.
  • Ask models to answer the generated questions using only each summary, then compare answers with the paper-grounded references using correctness, coverage, faithfulness, and cost measures.

Entry task: Select 20 arXiv papers from one field. Generate five grounded question-and-answer pairs and one summary per paper with a chosen LLM. Evaluate whether the questions can be answered from the summaries, and analyse at least three failure cases.

Target output: A reproducible benchmark for summary-based question answering over arXiv papers, a comparison of LLMs and summarisation techniques across corpora, and practical recommendations for generating informative scientific-paper summaries.

Multi-objective alignment for LLM fine-tuning

Master's thesis

Study how fine-tuning can optimise several alignment goals at once — helpfulness, factuality, safety, style, task success — instead of collapsing into one scalar reward.

alignmentfine-tuningParetoevaluation

Why this fits

  • Single-scalar rewards hide trade-offs: a helpful answer may not be the safest, a factual one may be less engaging.
  • Pareto-front exploration gives a principled way to reason about which alignment objective to sacrifice under which constraint.
  • Post-hoc profile switching (prompt- or logit-based) would let one base model serve several alignment regimes without retraining.

Suggested approach

  • Define 3–4 measurable alignment objectives with established benchmarks.
  • Fine-tune using constrained optimisation or scalarisation over multiple objective weightings.
  • Map the Pareto front; evaluate the diversity of the resulting model variants and the feasibility of post-hoc profile switching.

Entry task: Using a small instruction-tuned model and two alignment metrics (e.g. helpfulness and factuality), run fine-tuning at three objective weightings and report whether the trade-off is observable.

Target output: A characterisation of objective-pair tension, a Pareto-front map for at least one model family, and an evaluation of post-hoc profile switching.

REST API design and control primitives for AI agent systems

Master's thesis

Re-evaluate classic REST principles — HATEOAS, modularity, DRY, idempotency, least privilege, self-description — empirically for LLM agents that plan across calls. Extend with agent-control primitives (permission scoping, interruption hooks, state-transition constraints) that reduce unsafe or unrecoverable actions.

RESTHATEOASOpenAPIagent control

Why this fits

  • Hypermedia-driven navigation (HATEOAS) could let an agent complete novel tasks without prior API knowledge — but only if responses expose the right action links at the right granularity.
  • Agent workflows need first-class control primitives (interruption, scoped permissions, explicit state machines); the trade-off between thin and rich APIs is not empirically characterised.
  • Idempotency and least-privilege scoping are the cheapest available safety levers for agents that retry or loop; OpenAPI specs are the de facto machine-readable map for agent planning.

Suggested approach

  • Build a benchmark of multi-step tasks on a small REST API with measurable completion, error, and recovery rates.
  • Implement API variants at increasing richness: thin CRUD, HATEOAS-extended, and structured with explicit state-transition constraints and interruption hooks.
  • Run LLM agents across variants; measure task completion, error-type distribution, unsafe-action rate, and recovery behaviour.

Entry task: Take a small REST API and add HATEOAS links to all responses. Run an LLM agent on two tasks: one it has seen before, one it has not. Compare completion rates and error types with and without HATEOAS. As a second step, add an explicit state machine and compare agent recovery behaviour.

Target output: Empirically grounded design guidelines for REST APIs targeting LLM agent clients; a reusable benchmark comparing thin, HATEOAS, and control-primitive-rich API variants.

Minimal LLM agents for API-specific tasks: fine-tuning and model size

Master's thesis

General-purpose LLMs are expensive and brittle for API-bounded agent tasks. Study whether small fine-tuned models can reliably adhere to a specific API — and how minimal they can be while staying reliable on structured, API-specific workflows.

fine-tuningsmall modelsAPI adherenceagents

Why this fits

  • Large general-purpose models carry high inference cost and hallucinate endpoints and parameter types on domain-specific APIs at significant rates.
  • Fine-tuning on API-specific trajectories may teach a small model the structural constraints of an API far more efficiently than prompt engineering alone.
  • There is no systematic understanding of the minimum model capacity required for reliable API adherence in a bounded task domain.

Suggested approach

  • Define a benchmark of API-specific agent tasks with ground-truth correct call sequences for one or two target APIs.
  • Fine-tune models in the 1B–7B parameter range on synthetic and real API call trajectories; measure completion rate, error type, and recovery behaviour.
  • Systematically vary model size and fine-tuning data volume to characterise the capacity–reliability frontier.

Entry task: Fine-tune a small instruction-tuned model (1–3B parameters) on a synthetic dataset of correct API calls for one simple REST API. Compare completion rate and hallucinated-endpoint rate against a larger base model without fine-tuning.

Target output: A characterisation of the minimum model capacity needed for reliable API adherence; a fine-tuning recipe and benchmark reusable for other API domains. Complements the REST API design topic with a model-side perspective.

API design for search agents: minimal token burn, maximal search efficiency

Master's thesis or lab project

On top of the OUR²S search API and the chair's LLM endpoint, compare API design patterns for search agents — HATEOAS links, help texts, help functions, toolset size and result detail — and find the designs that minimise token use while maximising search success.

OUR²Ssearch agentsHATEOAStoken efficiency

Why this fits

  • Every tool definition and every result an agent reads costs tokens; for search agents that call the API many times per question, the API design dominates cost.
  • The OUR²S MCP redesign cut 25 tools to 3 and tool definitions from about 23.6k to 1.7k tokens, but which design choices matter most has not been measured systematically.
  • The owic25 evaluation corpus with its topics makes search success measurable, so token cost can be traded off against retrieval quality.

Suggested approach

  • Define a set of search tasks on the owic25 corpus with measurable success (relevant documents found, answer correctness).
  • Implement API variants over the OUR²S search API: flat tool catalogue, HATEOAS-style links to next actions, inline help texts, a separate help function, and different result detail levels.
  • Run agents on the chair's LLM endpoint across variants and measure tokens per task, calls per task, invalid calls, and search success.

Entry task: Using the OUR²S search API on owic25, run an agent on ten search tasks with two API variants (full help text in the tool description vs. a help function called on demand). Report tokens, calls and success per task.

Target output: Design guidelines for agent-facing search APIs with measured token/efficiency trade-offs; a reusable benchmark on owic25. Complements the REST API design topic with a search-specific, cost-focused perspective.

Optimising context usage: when and how agents should compact their context

Master's thesis or lab project

Long search and research tasks overflow an agent's context. Study when to compact, what to keep, and how to split state between context and harness (files, notes, memory), building on existing context-management methods such as JEV.

context managementcompactionagent harnesslong tasks

Why this fits

  • Agents on long tasks either run out of context or pay for tokens they no longer need; compaction loses information in ways that are rarely measured.
  • Harnesses can move state out of the context (files, wikis, goal lists), but the best division between context and harness is an open question.
  • Our own harnesses (e.g. the SOURCE harness, which compacts automatically) provide realistic long tasks and traces.

Suggested approach

  • Collect long search and research tasks with measurable outcomes, run in an agent harness with the chair's LLM endpoint.
  • Compare compaction triggers (fixed threshold, task phase, learned) and strategies (summaries, structured notes, external memory, selective retention).
  • Measure task success, tokens, and information lost at each compaction step.

Entry task: Run one long search task twice with an agent harness: once with compaction at a fixed context threshold, once with the agent writing structured notes to a file. Compare success, tokens and what each run forgot.

Target output: Context strategies for agents with measured cost and quality trade-offs; a set of long-task benchmarks for harness research.

Learning to rank and query quality for agentic search

Master's thesis

Build on OUR²S to improve retrieval quality for agents and the search strategies agents use: learning to rank from agent behaviour, query quality and reformulation, and the open question whether dense embeddings are needed for agentic search.

learning to rankOUR²Sagentic searchembeddings

Why this fits

  • Agents issue many more, and different, queries than people; rankings tuned for human queries may not serve them well.
  • Agent traces and relevance feedback in OUR²S provide training signals that do not exist for classic web search.
  • Dense retrieval is expensive at web scale; whether it pays off when an agent can reformulate and search repeatedly is unknown.

Suggested approach

  • Collect agent search traces on OUR²S (queries, reformulations, clicked or cited results) and derive training data.
  • Train learning-to-rank models on OUR²S features and compare sparse, dense and hybrid retrieval for agent queries.
  • Study search strategies: query quality prediction, reformulation policies, and when to stop searching; evaluate per search and per task.

Entry task: Run an agent on twenty questions against OUR²S with BM25 only and with hybrid retrieval. Log all queries, and report retrieval quality per query and task success per question.

Target output: Ranking models and search strategies for agents on OUR²S, with evidence on whether embeddings are needed for agentic search.

Efficient page-quality scores from static embeddings

Master's thesis

Estimate the quality of web pages with CPU-cheap static embeddings (e.g. model2vec) instead of transformer models, and test the estimate against human and LLM judgments across EU languages, not only against an existing proxy score.

static embeddingsmodel2vecpage qualitymultilingual

Why this fits

  • The Open Web Index computes a quality score with a small transformer that covers English pages only; at web scale, cost per page decides what can be scored at all.
  • Static embeddings run in about a millisecond per page on a single CPU core, but how much of page quality they capture is not known.
  • The existing score is itself a proxy; whether it agrees with human or LLM judgments, and whether any cheap model transfers to other languages, is open.

Suggested approach

  • Choose and compare quality targets: the existing proxy score, an LLM judge, and a small set of human labels; measure how far they agree.
  • Train small heads (ridge, MLP, kNN) on static embeddings, and test distilled or fine-tuned static models, aiming to close the gap to transformer embeddings at under 5 ms per page.
  • Evaluate per language on held-out judgments, including pages in languages where the proxy gives no score, and measure the effect on result ranking when quality is used for re-ranking.

Entry task: Take published Open Web Index pages with a quality score and a multilingual static embedding. Fit a ridge regression from embedding to score, report R² on held-out pages, and inspect the pages with the largest errors.

Target output: A fast multilingual quality estimator with measured cost, a comparison of quality targets (proxy, LLM, human), and an evaluation of its effect on ranking.

Open themes — apply with a one-pager

Open web search with OUR²S / YOARS

Open-ended research within the theme of transparent web retrieval and agentic search on the Open Web Index. You define the research question; selection is based on the quality of a one-page proposal.

Scope and application

  • Example directions: when query reformulation helps agentic search; sparse/dense/hybrid retrieval trade-offs; whether provenance improves LLM answer faithfulness.
  • Infrastructure: OUR²S (Open Web Index Retrieval Research System) and YOARS (Your Open Agent Relay System) — search API and corpora at ourrs.eu; University of Passau B2ACCESS login.
  • Apply with a one-pager: a concrete research question, why you are the right person, and a plausible evaluation strategy. Contact Prof. Granitzer before writing to align scope.
